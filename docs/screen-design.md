# 画面設計

最終更新: 2026-09-25

## 1. 目的と設計段階

本書は、社内購買・申請ワークフロー管理システムのMVPにおける画面構成、Route、主要操作、レスポンシブ方針を定義する。

実装前に変更コストの高い画面責務と遷移を決め、細かなComponent分割、余白、色、Data Fetchingの最終配置は各画面の実装とレビューで決める。

## 2. 画面設計の原則

- 申請者、承認者、購買担当者で業務目的の異なる画面はRouteを分ける
- 申請概要、明細、金額、履歴等の表示は、実際の重複を確認してから共通化する
- 一覧は対象を探す画面、詳細は内容を確認して業務操作を行う画面とする
- 承認、却下、発注、受領完了は、一覧から直接実行しない
- Roleによる表示制御はUXのために行い、最終認可はSpring Bootで保証する
- デスクトップとモバイルで業務上の操作ルールを変えず、配置だけを調整する
- Server Componentを既定とし、対話処理が必要なまとまりだけをClient Componentにする

## 3. App Router構成

```text
app/
├─ (public)/
│  └─ login/
└─ (protected)/
   ├─ layout.tsx
   ├─ dashboard/
   ├─ requests/
   │  ├─ new/
   │  └─ [requestId]/
   │     └─ edit/
   ├─ approvals/
   │  └─ [requestId]/
   ├─ purchases/
   │  └─ [requestId]/
   │     └─ order/
   └─ settings/
      └─ display/
```

### Routeの役割

| Route | 目的 |
| --- | --- |
| `/dashboard` | Roleごとの次の作業を要約する |
| `/requests` | 自分の申請を検索・確認する |
| `/requests/new` | 新しい申請または下書きを作る |
| `/requests/[requestId]` | 申請者として詳細を確認する |
| `/requests/[requestId]/edit` | 下書きを編集する |
| `/approvals` | 担当部門の承認待ちを検索する |
| `/approvals/[requestId]` | 承認者として詳細を確認し、承認・却下する |
| `/purchases` | 発注・受領対象を検索する |
| `/purchases/[requestId]` | 購買担当者として申請・発注状況を確認する |
| `/purchases/[requestId]/order` | 発注情報を入力して発注を確定する |
| `/settings/display` | Dashboardの表示順を設定する追加候補 |

同じ申請でもRoleごとに可能な操作と閲覧目的が異なるため、申請者・承認者・購買担当者の詳細Routeを分ける。発注は申請内容の編集ではなく、承認済み内容を参照して発注情報を新規記録する業務操作であるため、`edit` ではなく `order` とする。

## 4. 共通Layoutとナビゲーション

### 認証後Layout

- `app/(protected)/layout.tsx` を認証後画面の共通Layoutとする
- RoleごとのLayoutは最初から作らない
- 共通Layout自体はServer Componentにする
- サイドバー開閉、モバイルSheet等の対話部分だけをClient Componentにする
- Server Componentの `children` をClient Componentへ渡すCompositionを利用し、Client Boundaryを局所化する
- `"use client"` は可能な限り末端へ置くが、同じ対話状態を共有するまとまりまで不自然に分割しない

### デスクトップ

- 左サイドバーを表示する
- 明示的なボタンでアイコン表示へ折りたためる
- キーボード操作でも開閉できる
- 共通ヘッダーに画面名、ユーザー名、所属部門、Role、ログアウトを表示する

### モバイル

- ハンバーガーボタンから同じメニューをSheet表示する
- デスクトップと同じ権限・操作ルールを使用する
- Arc風の画面端hover表示はMVPに含めない

### メニュー

- ログインユーザーが利用可能な機能だけを表示する
- 複数Roleを持つユーザーには各Roleのメニューを表示する
- メニュー非表示だけを認可として扱わない

## 5. Dashboard

Dashboardは各一覧を複製せず、次に行う作業を要約する。検索Filterは専用一覧に配置する。

### USERセクション

- 新規申請への導線
- 最近更新された自分の申請5件
- ステータス別件数
- 自分の申請一覧へのリンク
- `DRAFT` は編集・削除、`SUBMITTED` は取消、それ以降は閲覧のみ

### APPROVERセクション

- 承認待ち件数
- 申請日が古い承認待ち5件
- 希望納期超過件数
- 承認待ち一覧へのリンク
- Dashboardから直接承認・却下しない

### PURCHASERセクション

- 発注待ち件数
- 受領待ち件数
- 希望納期が近い購買対象5件
- 購買対象一覧へのリンク
- Dashboardから直接発注・受領完了しない

複数Roleを持つ場合は該当セクションを縦に表示する。60時間側では固定順、70〜80時間側ではアカウントに保存する表示順設定を追加候補とする。

## 6. 一覧画面

### 共通方針

- サーバーサイドページングを使用し、無限スクロールは採用しない
- 表示件数は20、50、100件から選択し、初期値は20件とする
- 検索条件、ページ、表示件数、ソートをURLの `searchParams` に保持する
- 詳細から戻った場合も検索状態を復元する
- Loading、Skeleton、Empty、Error、再試行を用意する
- ページ切替時はTanStack Queryの `placeholderData` で直前の一覧を維持する候補とする
- 行の主要操作を1つ表示し、操作が増える場合は三点メニューへまとめる

### 検索操作

- キーワードは400〜500msのdebounce後に検索する
- IME変換中は検索しない
- ステータス、カテゴリ、仕入先等の単一選択は変更時に反映する
- 日付範囲、金額範囲等の複合条件は「検索」ボタンで確定する
- 「クリア」は条件を初期化して直ちに反映する
- 条件変更時は1ページ目へ戻し、URLは `router.replace` 相当で更新する
- 古い検索Requestはキャンセルするか、最新条件以外の結果を反映しない

### 自分の申請一覧

検索条件:

- ステータス
- キーワード（申請番号、タイトル、商品名）
- 作成日の範囲
- カテゴリ
- 仕入先

表示項目:

- 申請番号
- タイトル
- ステータス
- 明細概要
- 希望仕入先
- 合計金額
- 最終更新日時

初期ソートは最終更新日時の新しい順とする。

行操作:

- `DRAFT`: 詳細、編集、削除
- `SUBMITTED`: 詳細、取消
- その他: 詳細

### 承認待ち一覧

対象は `SUBMITTED` かつログイン承認者の担当部門内で、自己申請を除く。

検索条件:

- キーワード（申請番号、タイトル、商品名、申請者名）
- 申請日の範囲
- 申請部門
- カテゴリ
- 合計金額の範囲

表示項目:

- 申請番号
- 申請日
- 希望納期
- タイトル
- 申請部門
- 申請者
- 明細概要
- 希望仕入先
- 合計金額

初期ソートは申請日の古い順とする。希望納期は色だけでなく、「期限まで2日」「期限超過」等の文言でも示す。行操作は「詳細を確認」だけとし、一覧から承認・却下しない。

### 購買対象一覧

初期対象は `APPROVED` と `ORDERED` とし、検索条件で `COMPLETED` も選択可能にする。

検索条件:

- ステータス
- キーワード（申請番号、タイトル、商品名、申請者名）
- 申請部門
- 仕入先
- 承認日の範囲

表示項目:

- 申請番号
- タイトル
- ステータス
- 申請者・申請部門
- 明細概要
- 仕入先
- 合計金額
- 承認日
- 希望納期

初期ソートは希望納期の近い順とする。行操作は状態に応じて「発注内容を確認」「受領内容を確認」等の詳細遷移だけを提供する。

## 7. 詳細画面と操作配置

詳細画面には、申請番号、タイトル、ステータス、申請者、部門、希望納期、理由、全明細、金額、仕入先、操作履歴を表示する。

- 右側の常設操作パネルは設けない
- ページ内の申請番号・タイトル・ステータス付近に、現在可能な操作を表示する
- 操作ボタンを画面下部へ固定しない
- デスクトップではボタンをページ内ヘッダーの右側へ配置する
- モバイルではタイトル・ステータスの下へ縦または折返しで配置する
- 参照だけの状態では操作ボタンを表示しない

状態別の代表操作:

| 画面 | 状態 | 操作 |
| --- | --- | --- |
| 申請者詳細 | `DRAFT` | 編集、削除 |
| 申請者詳細 | `SUBMITTED` | 取消 |
| 承認詳細 | `SUBMITTED` | 承認、却下 |
| 購買詳細 | `APPROVED` | 発注処理へ |
| 購買詳細 | `ORDERED` | 受領完了 |
| 各詳細 | 処理済み | 結果と履歴の参照 |

承認・却下成功後は、検索条件を保持して承認待ち一覧へ戻る。成功Toastに処理済み詳細へのリンクを表示し、Undoは提供しない。

## 8. Dialogと専用画面

| 操作 | UI | 理由 |
| --- | --- | --- |
| 承認 | Dialog | 任意コメントと最終確認だけで完結する |
| 却下 | Dialog | 必須理由と最終確認だけで完結する |
| 取消 | Dialog | 必須理由と最終確認だけで完結する |
| 下書き削除 | AlertDialog | 破壊的操作の確認だけを行う |
| 受領完了 | Dialog | 受領日、任意備考、全商品受領確認を行う |
| 発注 | 専用画面 | 仕入先、発注番号、明細単価、納期等の入力が多い |

ここでいうDialogは、背景を操作できないモーダルダイアログを指す。focus移動、Tab操作、Esc、閉じた後のfocus復帰を確認する。

## 9. App Routerの共通UX

- Route単位で `loading.tsx`、`error.tsx`、`not-found.tsx` の配置を検討する
- 一覧と詳細にはSkeleton、Empty State、Error Stateを用意する
- 個別申請が存在しない、または閲覧範囲外の場合は404として扱う
- 機能自体を利用するRoleがない場合は403画面を表示する
- 詳細Metadataには申請番号を含める
- 詳細へのLinkは必要に応じてprefetchし、遷移待ち時間を確認する
- 未保存変更がある編集画面から離れる場合は確認する

## 10. 実装時に決める事項

- 各画面でServer Component + fetchとTanStack Queryのどちらを使うか
- Suspense Boundaryの粒度とDashboard取得の並列化
- 共通表示Componentを抽出する時期とprops
- モバイル一覧をTableの横スクロールにするかCard表示にするか
- 各Routeの `loading.tsx`、`error.tsx` の粒度
- Dashboard表示順設定をMVPへ含めるか

これらは画面ごとに、更新頻度、Client Cacheの価値、mutation後の更新方法、Client JS量、Waterfallを確認して決定する。
